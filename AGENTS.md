# AGENTS.md

Инструкции для AI-агентов и разработчиков, работающих в этом репозитории.
Читается вместе с `README.md` (пользовательская документация) и `PLAN.md` (план macOS-порта).

## Что это за проект

Неофициальный клиент Яндекс Музыки на Rust: Slint для интерфейса, Skia в программном
режиме (без GPU), rodio/symphonia для звука. Главная ценность — низкое потребление
памяти: ~65 МБ против ~850 МБ у официального Electron-клиента. Любые изменения,
добавляющие лишние копии данных или кэши без лимита, считаются регрессией.

- `origin` — апстрим `SpolzerMod/yamusic-rs` (Windows).
- `fork` — `rnikitin/yamusic-rs`; ветка `macos` — платформенный слой и macOS-специфика.
- Rust 2021, `rust-version = 1.92` в `Cargo.toml`. Не использовать возможности новее.

## Обязательный рабочий процесс

В окружении установлены `karpathy-guidelines` и набор superpowers. Для этого репо они
обязательны, а не опциональны. Если скилл применим — сначала загрузить его, потом
задавать вопросы, читать код или запускать команды.

- `karpathy-guidelines` — базовая дисциплина при любом написании, ревью и
  рефакторинге кода: явно озвучивать допущения, не усложнять, не трогать соседний
  код, доводить задачу до проверяемого критерия.
- `using-superpowers` — точка входа в процесс superpowers. Процессные скиллы идут
  раньше предметных.

**Новая функциональность:**

1. `brainstorming` — до любого кода: контекст, вопросы, 2–3 варианта, дизайн и
   согласование с пользователем.
2. `writing-plans` — план по утверждённому дизайну.
3. `executing-plans` (или `subagent-driven-development` для независимых задач) —
   выполнение плана с проверками на каждом шаге.
4. `test-driven-development` — тест раньше реализации везде, где логика тестируема.
5. `verification-before-completion` — перед заявлением о готовности.

**Багфикс или неожиданное поведение:**

1. `systematic-debugging` — сначала воспроизведение и корневая причина. Никаких
   фиксов по симптому до завершения investigation.
2. `test-driven-development` — регрессионный тест, который падает до фикса.
3. `verification-before-completion` — прикладывать вывод команд, а не обещания.

Дополнительно: `using-git-worktrees` — если нужна изоляция работы;
`requesting-code-review` / `receiving-code-review` — перед мержем и при получении
замечаний; `finishing-a-development-branch` — при завершении ветки;
`dispatching-parallel-agents` — только для действительно независимых задач.

Пропускать процесс можно только по явной просьбе пользователя. Если инструкции
скилла конфликтуют с этим файлом, приоритет у `AGENTS.md`.

## Сборка и проверка

Требования: Rust 1.92+ и Xcode Command Line Tools. Форк собирает только macOS; код
Windows и Linux остался от апстрима и здесь не собирается и не проверяется.

```bash
cargo build --release          # первый раз 5–10 минут: Skia + LTO
cargo run                      # debug: лог дублируется в консоль
tools/make_app.sh              # macOS .app-бандл (--debug для debug-сборки)
tools/make_dmg.sh              # .dmg из готового .app: ярлык «Программы» рядом
```

Проверки, которые обязаны проходить (то же делает CI в `.github/workflows/build.yml`):

```bash
cargo clippy --release --all-targets -- -D warnings
cargo test --release
cargo build --release
```

CI гоняется на macOS (`macos-15-intel`): clippy, тесты, universal `.app` и `.dmg`. Это
авторитетная проверка для macOS. Windows и Linux в этом форке не собираются — их сборки
живут в апстриме, поэтому Windows- и Linux-only код локально ничем не проверяется: держать
его под `cfg`-гейтами и не ломать чужие ветки — ответственность автора правки.

Если `skia-bindings` не может скачать бинарники Skia:

```bash
SKIA_BINARIES_URL=file:///путь/к/skia.tar.gz cargo build --release
```

## Архитектура

| Файл | Ответственность |
| --- | --- |
| `src/main.rs` | Точка входа: единственный экземпляр, выбор backend/renderer, запуск окна. |
| `src/gui.rs`, `src/gui/landing_ui.rs` | Связь Slint с данными: страницы, меню, настройки. Большой файл — менять точечно. |
| `src/api.rs` | Запросы к API: каталог, лайки, плейлисты, волна, стримы, LRC. |
| `src/client.rs` | Всё, что Яндекс может поменять: OAuth-клиент, ключи подписи, заголовки. Ломается API — править здесь. |
| `src/player.rs` | Аудиодвижок в отдельном потоке: очередь, предзагрузка, сессии волны, фидбек. |
| `src/stream.rs` | `Read + Seek` поверх HTTP Range: воспроизведение без полной загрузки трека. |
| `src/landing.rs` | Страницы из серверных блоков («Для вас», «Концерты», «Книги и подкасты»). |
| `src/assets.rs`, `src/i18n.rs` | Шрифты, спрайт иконок, словари из `app.asar` или веб-версии. |
| `src/images.rs`, `src/net.rs` | Фоновые загрузки и кэши с бюджетом памяти. |
| `src/win.rs`, `src/tray.rs` | Платформенные фасады; реализации в `windows.rs` / `unix.rs` по `cfg`. |
| `src/mac.rs` | macOS: медиа-клавиши, «Сейчас играет», нативное окно — напрямую через objc runtime. |
| `src/secret.rs`, `src/config.rs` | Токены (DPAPI на Windows), `config.json`, папка данных, лог. |
| `src/discord.rs`, `src/update.rs` | Rich Presence через локальный канал; проверка релизов и замена exe. |
| `ui/app.slint` | Входная точка UI, компилируется `build.rs` со стилем fluent. |
| `tools/` | Генераторы темы/палитры и сборка macOS-бандла. |

Платформенный слой устроен как фасад: `win.rs` и `tray.rs` реэкспортируют модуль по
`cfg`. Новый платформенный код кладётся в соответствующий подмодуль, а не в общий код.
На macOS окном управляет slint/winit, поэтому HWND-заглушки возвращают 0 — это норма.

## Правила кода

- **Язык.** Комментарии, doc-комментарии и сообщения об ошибках — по-русски, как в репо.
  Пользовательские строки интерфейса — русские: они же служат ключами для `i18n::tr`.
  Новые ключи не выдумывать: словарь берётся из оригинального приложения.
- **Стиль.** Отдельного `rustfmt.toml` нет; длинные строки и плотный код — норма.
  Не делать массовый `cargo fmt`: диффы должны быть минимальными и по делу.
- **Doc-комментарии.** У модулей — `//!` с назначением; у неочевидных решений — `///`
  с причиной («почему», а не «что»). Существующие комментарии не удалять без причины.
- **Предупреждения.** Clippy с `-D warnings` — обязателен. Не подавлять предупреждения
  без комментария-обоснования; для платформенных заглушек есть `allow(dead_code)`.
- **Зависимости.** Список зависимостей намеренно маленький. Новый крейт — только если
  задачу нельзя решить средствами std/уже подключённых библиотек. Для macOS API уже
  используются прямые вызовы objc runtime без сторонних крейтов.
- **Unsafe/FFI.** Win32 и objc-вызовы держать внутри платформенных модулей, проверять
  указатели и `respondsToSelector` там, где API приватное. В общий код `unsafe` не тащить.
- **Память.** Не клонировать большие буферы без необходимости, не держать кэши без
  лимита, не включать `cache-rendering-hint` без гейтинга по видимости. Это главная
  фича проекта, а не микрооптимизация.
- **Сгенерированное не править.** `ui/theme.slint` и `src/palette.rs` созданы
  `tools/gen_theme.py` и `tools/gen_palette.py`. Менять нужно генератор и перегенерировать.
- **Имя приложения.** Задаётся один раз в `build.rs` (`APP_NAME`), в коде доступно как
  `env!("APP_NAME")`. Не дублировать строку в других местах.
- **Версия.** `version` в `Cargo.toml` должна совпадать с тегом `vX.Y.Z`; CI проверяет это
  перед релизом. `Cargo.lock` коммитится вместе с изменением зависимостей.

## Тесты

- Юнит-тесты лежат в конце модуля: `#[cfg(test)] mod tests { ... }`.
- Тестировать чистую логику: парсинг LRC, подпись запросов, размеры обложек, теги,
  обновления, склонения. Тесты не должны ходить в сеть.
- Сетевые тесты помечены `#[ignore]` и требуют входа в аккаунт; запускать вручную:
  `cargo test --release -- --ignored`.
- GUI, звук, трей и интеграции юнит-тестами не покрыты. Для них нужна ручная проверка
  на целевой ОС; для UI-изменений — запуск приложения, а не только `cargo check`.

## Платформенные особенности

- Windows: трей, единственный экземпляр через мьютекс, DPAPI, автозапуск через реестр,
  самообновление заменой exe.
- macOS: трея нет (`--tray` игнорируется), токен хранится открытым текстом как
  не-Windows фолбэк апстрима, обновление открывает страницу релиза, окно — нативное
  («светофор», скруглённые углы, медиа-клавиши).
- Linux официально не поддерживается; слой `unix` заточен под macOS (`defaults`,
  LaunchAgent). Не выдавать macOS-код за кроссплатформенный.

## Git и планы

- Сообщения коммитов — по-русски, коротко, с областью: `README: ...`,
  `macOS-порт: ...`, `Плеер: ...`. Без Conventional Commits.
- Не коммитить `target/`, локальные конфиги и токены. Папка данных приложения лежит
  вне репозитория: `%APPDATA%\yamusic-rs` или `~/Library/Application Support/yamusic-rs`.
- `PLAN.md` — живой план macOS-порта; `plan/*.md` — ExecPlan по снижению памяти.
  При работе по плану обновлять его разделы `Progress`, `Surprises & Discoveries`,
  `Decision Log`, `Outcomes & Retrospective`. Не смешивать два плана.
- Новые спеки и планы фич складывать в `plan/` с именем `YYYY-MM-DD-<тема>.md`.
  Это переопределяет дефолтные пути `docs/superpowers/` из скиллов.
- В рабочем дереве могут быть незакоммиченные изменения и неотслеживаемые файлы —
  считать их работой пользователя и не откатывать.

## Перед завершением задачи

1. `cargo clippy --release --all-targets -- -D warnings` — без предупреждений.
2. `cargo test --release` — все тесты проходят.
3. Изменение собрано и вручную проверено на затронутой платформе (UI/звук/трей).
4. Не изменены сгенерированные файлы, `target/` и чужие незакоммиченные правки.
5. Если поведение видно пользователю — обновлён `README.md`; если закрыт пункт плана —
   обновлён соответствующий план.
6. Процесс пройден: для фичи — `brainstorming` и план, для бага — `systematic-debugging`;
   перед ответом — `verification-before-completion` с выводом проверок.
